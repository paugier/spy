# Metaclasses written in SPy (experiment)

Tentative implementations of the metaclasses of `metaclasses.md` (section 6). They
replace the experiments of `stdlib/class_modifiers/` (decorators, hooks `__transform__`,
`__define__`...), which the plan abandons.

**None of this runs.** The goal is to check that the plan is robust, by writing the
code that it promises, and to show what it allows. Everything that does not exist in SPy
today is invented, and listed below.

| File                  | Metaclass        | Milestone | Needs (besides the invented API below)                        |
| --------------------- | ---------------- | --------- | ------------------------------------------------------------- |
| `record.spy`          | `Record`         | 1         | `P3`, `P4`, `P5`, `P6`, `M1.1`-`M1.6` (`M2.2` for `implements`)  |
| `class_metaclass.spy` | `ClassMetaClass` | 2         | `M2.1`, `M2.2`, `issubclass`                                  |
| `dataclass.spy`       | `DataClass`      | 2         | `class_metaclass.spy`                                         |
| `protocol.spy`        | `Protocol`       | 2         | `M2.1`, `Method.bind` (finding 4)                             |
| `variant.spy`         | `Variant`        | 2         | `M2.1`, `M2.4`, `ll_union` with named members                 |
| `_metaclass_helpers.spy` | (helpers)     |           | shared by all of the above                                    |

The usage example of each metaclass is in the docstring of its file. The runnable-in-
principle example (tests skipped until the features exist) is `examples/exp_record`.

## Invented API (in addition to section 5 of `metaclasses.md`)

- `body.attrs`, `body.add_attr(name, value)`: class attributes that are neither fields
  nor functions (a nested `class`, a blue constant such as `__info__`).
- `body.defaults`: `{name: value}` for the fields that have a default (`M1.7`).
- `body.methods` yields **`Method`** objects, not bare functions: `.argtypes` (without
  `self`), `.restype`, `.is_required` (the body is `...`), `.bind(T)` (the same function
  with `self` typed as `T`). See finding 4.
- `T.__fields__`: ordered `{name: type}` of the *logical* fields of any type. For a
  `Record`, `x` and `y`, not `__ll__`.
- `cls.w_base`, `issubclass`, `isinstance(T, M)`, `StructType.declare(fqn)`,
  `Data.define_from_classbody(body)`, `self.fqn.join(...)`, `cls.__name__`.
- Class keyword arguments: `define_from_classbody(self, body, final=False, implements=())`.
- Low level (as in `inheritance-variants-protocols.md`): `FnPtr`, `static_ptr`,
  `ptr_cast`, `addr_of`, `void`, `ll_union(cases)`.
- Blue-level conventions: a blue struct value (a vtable) turned into a constant in static
  memory by `addr_of`; a function converted to a `FnPtr` slot; `unroll_range(N)` with the
  blue indexing `names[i]`; `*args: *types` with `types[:n]` slices.

## What holds up

1. **The order "wrapper first, data after" is already supported by the compiler.**
   `gc_ptr[Data]` of a declared but undefined struct works: `W_PtrType.from_itemtype`
   leaves it not ready and `W_StructType._backfill_ptr_fields` completes it when `Data`
   is defined. `calc_layout` only needs `sizeof` of the fields. The same order is used
   three times (`Record`, `ClassMetaClass`: wrapper, vtable, object; `Variant`).
2. **Orthogonal metaclasses and helper functions are enough.** Nothing is a stacked
   transformer. The helpers (answer to question 6) are five blue functions that take the
   body or the wrapper to complete, plus `cls` and `fields`: `add_generated_methods`
   (`__init__`, `__eq__`, `__ne__`, `__repr__`), `add_field_accessors`, `add_identity`,
   `add_erase_methods`, `add_protocol_defaults`. `Record`, `ClassMetaClass` and
   `DataClass` share almost everything through them.
3. **`final` needs no field of the type (`M2.3`) for this metaclass.** `ClassMetaClass`
   keeps its information in a class attribute `__info__` (a blue dict), which a subclass
   reads when it is defined (`base.__info__["final"]`) and which the dispatchers use
   when they are generated. The call resolution is in the metaclass, as the note hopes:
   a final class gets direct dispatchers, a non-final one gets vtable dispatchers, and a
   final class without base gets no vtable pointer at all.
4. **Protocol and Variant fit the same scheme** (a wrapper, a second struct, hooks as
   `metafunc`s), and `Variant` answers the open question "what is `Shape.Circle`":
   the metaclass makes it the constructor, and offers `__tag__`, `__as_<Case>__` as the
   hooks that `match` would use.

## Problems found

1. **There is no metaclass for value structs.** `StructRecord` was removed. `__init__`
   cannot be generated for a value: a struct is immutable and `self` is a copy (the
   constructor is `__new__ = __make__`). `__eq__` and `__ne__` are already generated by
   `StructType`, and defining `__eq__` by hand sets `spy_key_is_valid = False`, so the
   struct could no longer be an argument of a blue function. Nothing worth a metaclass
   is left.
2. **`Record` needs more than section 4 shows.** `__is__` (otherwise `p is q` is
   rejected on a struct), `__ne__` (once `__eq__` is defined the compiler does not
   generate `__ne__`: `lazy_define_from_classbody`), and the pair `__erase__` /
   `__unerase__`, which is the contract with `Protocol` (without it, the `Circle_data` of
   the page on protocols comes from nowhere).
3. **The API of `ClassBody` is incomplete.** Needed and missing from section 5:
   `attrs` / `add_attr` (variant cases, `__info__`, `__fields__`, protocol requirements),
   `defaults`, and a way to read the logical fields of any type (`__fields__`).
   `StructType.declare` must also uniquify the FQN and register the type as a global
   (`fwdecl_ClassDef` does both: `get_unique_FQN` and `vm.add_global`), otherwise the C
   backend never emits `Point::Data`.
4. **Methods are typed with the declared type, which blocks default methods of
   protocols.** The default method `show` of a protocol is typed `self: Shape` (the fat
   pointer), and has to become a method of each class that conforms (`self: Circle`).
   `Method.bind(T)` is the invented answer, and it means re-typing a function from its
   AST: the "method template" problem of the old `@heap` experiment, which the plan of
   section 2 (typing the methods once with the declared type) does not solve. The same
   `Method` object also has to give the signature (`argtypes`, `restype`), which
   `ClassMetaClass` needs for the slots of the vtable and `Protocol` for its table.
5. **Explicit conformance contradicts the rule of metaclass compatibility.**
   `class Circle(Shape)` with `Shape` a `Protocol` is rejected by "the metaclass of a
   class with bases must be a subtype of the metaclass of the bases", since `Record` is
   not a subtype of `Protocol`. I used `class Circle(metaclass=Record, implements=[Shape])`
   (a keyword handled by `add_protocol_defaults`). Consequences: `M2.2` (keywords in a class statement) is needed by `Record` as soon as
   protocols exist (milestone 2), not before. That also settles the spelling question of
   section 5.8 of the other note.
6. **A zero-size field breaks `calc_layout`.** With `field_size == 0`, the alignment
   `(offset + (field_size - 1)) & ~(field_size - 1)` gives 0, so the offset goes back to 0
   and the following fields overlap the previous ones. It matters here: the vtable of a
   root class without virtual methods is an empty struct, and `__parent__: VTable` of a
   subclass is then a zero-size field. (C also rejects empty structs.) Either give empty
   structs a size of 1, or skip them.
7. **Modules are flat.** `find_file_on_path` looks for `{modname}.spy` in each directory
   of `vm.path`: no packages. `stdlib/metaclasses/` is therefore not importable as
   `metaclasses.record`. The tests of `examples/exp_record` add the directory to
   `vm.path`, and the files are imported by their bare names (`record`, `protocol`,
   `variant`, `dataclass`, which would be top-level names and could collide). Either
   packages come first, or the files get a prefix.
   Related, minor: a `@blue.generic` without parameter, to be "called with `[]`", cannot
   be written (`f[]` is not valid Python, so not parsable by SPy). `ClassMetaClass` gives
   its generic a dummy parameter (`vtable[cls]`).
8. **The parser refuses bases and keywords** (`base classes not supported yet`, `keywords
   in classes not supported yet`, in `_parse_py_classdef`), and `ClassFrame` accepts only
   `VarDef`, `AssignLocal`, `If`, `Pass` and `FuncDef`: no nested class (`M2.4`), no
   `for`. The files avoid the second limit by building everything in the metaclass, not
   in the body of the user's class.
9. **`w_base` of a class without base** has to be decided (`object`? `None`?): the
   code tests `base is object`. `isinstance(base, ClassMetaClass)` and `issubclass(Sub,
   cls)` (for the free upcast of `__convert_from__`) have to be provided from `w_base`.
10. **Not handled**: default values with the generated `__init__` of heap classes (the
    `*args: *types` form has no place for them), `super().method()` inside a user
    method of a class with a vtable, static and class methods (every name without a
    dunder is virtual), conversion of a `Protocol` to a smaller `Protocol`, and a
    variant by value.
